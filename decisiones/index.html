Antes del mock final · 7 decisiones de contrato

Lo que falta cerrar.

Correlación del contrato propuesto contra Mercado Libre y Amazon SP-API. Cuatro de las 7 decisiones bloquean la versión final del mock (4); tres son defaults razonables. Cada una viene con tres opciones (A recomendada, B alternativa, C descartable).

Formato del `errors[]` en validaciones

¿Los errores por campo usan JSON Pointer (RFC 6901) tipo `/items/0/attributes/3`, o un path dot-notation tipo `items.0.attributes.3.value`?

Origen: Mercado Libre devuelve dot-notation; Amazon devuelve JSON Pointer en Feeds API. Ambos funcionan pero cambian la lógica del SDK del seller.

Opción ARecomendada

JSON Pointer (RFC 6901)

Estándar IETF, se parsea con cualquier librería genérica, consistente con lo que ya hace Amazon Feeds. Formato: `/items/0/attributes/3`.

Opción BAlternativa

Dot-notation con índices

Más legible visualmente para debug humano. Formato: `items.0.attributes.3.value`. Lo usan Mercado Libre, Shopify, parcialmente Stripe.

Opción CNo recomendada

Ambos (duplicados en el payload)

Response payload crece ~30%. Un dev tiene que elegir cuál usa; genera código inconsistente entre equipos.

Semántica del PATCH para corregir propuesta

¿`PATCH /proposals/{id}` usa JSON Merge Patch (RFC 7396) o JSON Patch (RFC 6902)?

Origen: Amazon SP-API usa JSON Patch (ops). Mercado Libre usa Merge Patch. Es la decisión más visible: cambia completamente la forma del request body.

Opción ARecomendada

JSON Merge Patch (RFC 7396)

El request body es un objeto parcial con los campos a cambiar. Simple de generar y leer. `null` significa borrar. Lo usa Mercado Libre.

Opción BAlternativa

JSON Patch (RFC 6902)

El request es un array de operaciones (`op`, `path`, `value`). Más expresivo pero verbose. Lo usa Amazon.

Opción CNo recomendada

PUT (reemplazo completo)

El seller manda la propuesta entera cada vez. Simple pero el payload es enorme y pierde la noción de «qué estoy corrigiendo».

Formato de las fechas en los avisos

¿Los `createdAt`, `publishedAt`, `effectiveFrom` usan ISO 8601 con zona UTC (`2026-10-19T20:00:00Z`) o incluyen offset (`-06:00`)?

Origen: Mercado Libre: offset. Amazon: UTC. UTC es más simple de serializar; offset preserva la intención del origen (CDMX vs. Guadalajara vs. Tijuana).

Opción ARecomendada

ISO 8601 UTC (`Z`)

Formato: `2026-10-19T20:00:00Z`. Simple, se parsea igual en todos los lenguajes. El seller formatea en su zona si quiere.

Opción BAlternativa

ISO 8601 con offset local

Formato: `2026-10-19T14:00:00-06:00`. Preserva la hora original pero obliga al seller a normalizar antes de comparar.

Opción CNo recomendada

Epoch en milisegundos

Un número (`1792464000000`). Compacto pero ilegible y pierde la zona.

Enum `allowedAction` para productos existentes

¿Cuáles son los valores exactos del enum `allowedAction` que devuelve `GET /products/search` cuando el producto ya existe?

Origen: Mercado Libre tiene 6 (CREATE_PROPOSAL, CREATE_OFFER, MULTI_OFFER, STOCK_OUT_OFFER, REQUEST_EAN_RELEASE, NOT_ALLOWED). Amazon tiene 3. Mientras no cerremos esto, el seller no sabe qué hacer con un GTIN colisionado.

Opción ARecomendada

6 valores (como MELI)

CREATE_PROPOSAL, CREATE_OFFER, MULTI_OFFER, STOCK_OUT_OFFER, REQUEST_EAN_RELEASE, NOT_ALLOWED. Cubre todos los casos del Mercado Libre playbook.

Opción BAlternativa

3 valores + razón libre

CREATE, UPDATE, DENIED. Más simple pero obliga a parsear strings libres para explicar el por qué.

Opción CNo recomendada

Boolean `canCatalog` + reason

Mínimo viable. Pierde toda la riqueza de casos (p. ej. permitir solo oferta nueva vs. multioferta).

05
Default razonable

Idempotency-Key en operaciones de escritura

¿Es obligatorio o opcional en `POST /proposals` y `POST /batches`?

Origen: Stripe lo obliga; AWS no. Mercado Libre tampoco lo pide. Si lo hacemos opcional, podemos tener duplicados en reintentos.

Opción ARecomendada

Obligatorio (400 si falta)

Garantiza no-duplicación. El seller tiene que generar un UUID por operación. Documentar bien o es fricción.

Opción BAlternativa

Opcional pero recomendado

El PIM dedup por `externalRef` si no se manda. Protege a sellers básicos pero deja la puerta abierta a edge cases.

06
Default razonable

Rate limiting · header con los límites

¿Devolvemos `X-RateLimit-Limit`, `X-RateLimit-Remaining`, `X-RateLimit-Reset` en cada respuesta?

Origen: Convención de GitHub, Stripe, Slack. Mercado Libre no lo hace, Amazon tampoco. Pero facilita el debugging del seller.

Opción ARecomendada

Sí, siempre

El seller puede ajustar su concurrencia sin tener que llamar `GET /me`. Pequeño costo de ancho de banda.

Opción BAlternativa

Sólo en 429

Baja ruido en respuestas normales. El seller no sabe cuándo se va a chocar hasta que lo hace.

07
Cosmética

Formato de los IDs internos

¿`proposalId`, `batchId`, `productId` son UUIDs, ULIDs, o strings con prefijo humano (`PROP-000123`)?

Origen: Mercado Libre usa números largos. Amazon usa UUIDs. Stripe usa strings con prefijo (`cus_abc123`). El prefijo humano se debugguea mejor en logs.

Opción ARecomendada

String con prefijo humano

`PROP-000123`, `BATCH-000045`, `PRD-DEMO-0009`. Se identifica a simple vista. Pequeño overhead de generación.

Opción BAlternativa

ULID

Ordenado por tiempo, globalmente único, 26 chars. Mejor que UUID para logs. Menos humano que el prefijo.

Opción CAlternativa

UUID v4

Estándar universal. Pero ilegible en logs y no transmite nada del tipo de recurso.
